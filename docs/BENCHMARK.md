# Бенчмарк ресурсов rt-ui

> Статус: **методика и предварительные цифры**. Полный прогон делаем после того, как порт и упаковка завершены (этап 12 в [`PLAN.md`](PLAN.md)),
> потому что размер и скорость зависят от итогового набора компонентов. Скрипты живут в `tools/bench/`, результаты попадают в этот файл.

## 1. Что хотим узнать

| Вопрос | Метрика |
|---|---|
| Сколько весит библиотека в бандле приложения? | JS и CSS: raw / gzip / brotli — для сценариев «одна кнопка», «форма», «таблица», «вся библиотека» |
| Платим ли мы за то, что берём только нужное? | tree-shaking: размер растёт пропорционально используемым компонентам? |
| Сколько стоит CSS в браузере? | разбор и пересчёт стилей, размер CSSOM, доля реально используемых правил (CSS coverage) |
| Как быстро монтируются и обновляются компоненты? | время монтирования N экземпляров, время обновления, число DOM-узлов |
| Как ведёт себя таблица — главный компонент CRM? | 100 / 1 000 / 10 000 строк: первый рендер, прокрутка (кадры), сортировка, выбор всех, память |
| Сколько памяти? | JS heap, число DOM-узлов и слушателей, утечки после многократного открытия/закрытия попапов |
| Насколько это дороже/дешевле «голого» фреймворка? | нулевой бандл: Svelte vs React (hello-world), чтобы отделить цену фреймворка от цены библиотеки |

## 2. Методика

* **Только production-сборка** (`vite build` + `vite preview`), не dev-сервер. Отдельное приложение `tools/bench/app` с входом на каждый сценарий, чтобы размер измерялся честно.
* **Размер:** сумма чанков, которые грузит сценарий; отдельно JS и CSS; raw, gzip (уровень 9), brotli (уровень 11). CSS — минифицированный (Lightning CSS); шрифты — отдельной строкой (woff2).
* **Браузерные метрики:** Playwright + CDP (`Performance.getMetrics`: `ScriptDuration`, `RecalcStyleDuration`, `LayoutDuration`, `TaskDuration`; `Memory.getDOMCounters`; `performance.memory`),
  трассировка для длинных задач, CSS coverage (`Profiler`/`CSS.startRuleUsageTracking`) для доли используемых правил.
* **Стабильность:** каждый замер — медиана и разброс минимум из 15 запусков после 3 прогревочных; профиль CPU без троттлинга и с троттлингом 4× (слабый ноутбук вуза); одна и та же машина, закрытые лишние процессы.
* **Кадры прокрутки:** программная прокрутка контейнера таблицы и подсчёт кадров `requestAnimationFrame` (fps, доля кадров дольше 16,7 мс).
* **Утечки:** 200 циклов открыть/закрыть (Popover, Select, Modal); heap после GC не должен расти линейно.
* **Сравнение:** внутри проекта — до/после оптимизаций; с внешним миром — «нулевой» Svelte и React (hello-world, те же инструменты сборки), чтобы показать цену фреймворка отдельно.
  Прямое сравнение с настоящими React-компонентами Ростелекома невозможно (пакет закрыт), а эталонный Storybook включает свой тяжёлый рантайм, поэтому это сравнение мы не делаем и честно об этом пишем.

## 3. Предварительные цифры (уже измерены; полный бенчмарк их уточнит)

Стили дизайн-системы (минифицированный CSS, Lightning CSS), КБ:

| Пакет стилей | raw | gzip | brotli |
|---|---|---|---|
| CSS всех компонентов | 1483 | 69 | 38 |
| CSS одной темы | 176 | 16 | 12 |
| **Все компоненты + одна тема** (+ `TableGrid`, `Tree`, `SideMenu`) | **1706** | **90** | **55** |
| Все компоненты + **все четыре темы** | 2233 | 137 | 57 |

Шрифт Rostelecom Basis (woff2): по ~47 КБ на начертание (Regular, Medium, Bold); Light — только woff.

**Что это значит.**
* По сети вся дизайн-система в стилях — порядка 55 КБ brotli: небольшая цена. Четыре темы вместе почти не тяжелее одной (57 против 55 КБ brotli): темы отличаются лишь значениями токенов, и они хорошо сжимаются.
* Основной вопрос не размер по сети, а **стоимость разбора 1,7 МБ CSS в браузере** и то, сколько правил реально используется на экране. Именно это покажут замеры разбора/пересчёта стилей и CSS coverage.
* Возможные оптимизации, которые мы измерим: раздельная поставка CSS по компонентам (подключать только используемые), поставка только нужной темы, минификация токенов, удаление неиспользуемых токенов.

#### Tree-shaking: одна кнопка напрямую и через barrel

| Вариант | JS raw, КБ | JS br, КБ | модулей `src/lib` в бандле | модулей всего |
|---|---:|---:|---:|---:|
| S1: `import Button from …/Button.svelte` (прямой импорт) | 39.7 | 13.9 | 6 | 103 |
| S1b: `import { Button } from src/lib/index.ts` (barrel, поле `sideEffects` из package.json) | 39.7 | 13.9 | 6 | 103 |
| S1n: то же, но `sideEffects` игнорируется (что было бы без поля) | 132.6 | 36.1 | 1587 | 1749 |

Barrel не тяжелее прямого импорта (разница 0 Б), то есть tree-shaking через `src/lib/index.ts` работает: его обеспечивает поле `"sideEffects": ["**/*.css"]` в `package.json`. Без этого поля (S1n) barrel тащил бы 92.9 КБ лишнего JS (×3.3).

## 4. Критерии и «бюджеты» (черновик, уточним после первого прогона)

* Форма CRM (S2), JS + CSS одной темы: **≤ 100 КБ brotli** без шрифтов.
* Первый рендер таблицы на 1 000 строк: **≤ 150 мс** на десктопе; прокрутка 10 000 строк с виртуализацией: **≥ 55 fps**.
* Утечек нет: heap после 200 циклов открытия/закрытия попапа растёт **< 5%**.
* Повторное монтирование 1 000 кнопок: **≤ 30 мс**.

## 5. Как запустить (после реализации `tools/bench/`)

```bash
(cd tools/bench && npm install)   # один раз: react/react-dom для сценария S0r (остальное берётся из корневого node_modules)
npm run bench:size      # сборка сценариев S0–S5 и таблица размеров (raw/gzip/brotli)
npm run bench:runtime   # Playwright + CDP: время, память, кадры, coverage
npm run bench:report    # обновить таблицы в docs/BENCHMARK.md
```

Полный прогон `bench:runtime` (15 запусков после 3 прогревочных, проходы CPU ×1 и ×4) идёт долго и требует простаивающей машины;
флаги (`--runs`, `--warmup`, `--throttle`, `--only`, `--rows` ...) и устройство harness описаны в [`tools/bench/README.md`](../tools/bench/README.md);
для проверки скриптов: `npm run bench:runtime -- --runs 1 --warmup 0 --throttle 0 --rows 100 --leak-cycles 20`.

## 6. Окружение прогона (заполняется автоматически)
