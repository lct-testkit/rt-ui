# TableGrid: профиль, правки и результаты

Дата: 2026-09-20. Машина: AMD Ryzen 7 2700 (16 потоков), Windows 11, Chromium 120 (Playwright 1.40), production-сборки Vite 8 / Svelte 5.57 сценария S3 (`tools/bench/app/scenarios/s3`).
Числа сняты официальным харнесом `tools/bench/runtime.py --only table --runs 3 --warmup 1 --throttle 0 --big-runs 1` («до» — оригинальные исходники TableGrid, «после» — текущие,
оба собраны в один и тот же сценарий S3 и прогнаны подряд).

> Во время замеров машина была занята другими процессами (~35 % CPU), поэтому **абсолютные числа завышены в 1,5–3 раза**; смотрите на соотношения «до → после» и на профили.
> 10 000 строк в режиме `all` — один запуск (несколько минут на запуск).

## 1. Итог

* **Режим `virtual` заработал** (раньше тело таблицы было невидимо: ячейки складывались в колонку 80 px внутри списка нулевой высоты). Теперь 10 000 строк: первый рендер 186 (1000 строк — 100) мс,
  в DOM ~31 строка, прокрутка **60 кадров/с** (p95 кадра 16,7 мс, 0 медленных кадров), память ~8 МБ; сортировка 62 мс, «выбрать всё» 52 мс.
  Бюджеты из `docs/BENCHMARK.md`: прокрутка 10 000 строк ≥ 55 fps — **выполнен**; первый рендер 1000 строк ≤ 150 мс — **выполнен** (100 мс на 1000 строк на загруженной машине; 186 мс на 10 000).
* **Режим `all` (все строки в DOM) ускорен по JS, но не по браузеру.** На 1000 строк JS (`script`) 1 345 → 933 мс (−31 %), память 82 → 55 МБ, слушателей событий 24 107 → 113, узлов DOM 128 k → 75 k,
  но первый рендер 2,69 → 2,30 с (−14 %), а сортировка / «выбрать всё» / раскрытие не изменились (≈ 1,8 / 0,56 / 0,85 с): **две трети времени — это пересчёт стилей и раскладка ~19 000 элементов самим браузером**
  (style + layout ≈ 1,9 с против 0,93 с JS; см. §4), а DOM и CSS таблицы обязаны совпадать с React-оригиналом. Цель «≥ 10× на 1000 строк без виртуализации» при неизменном DOM / CSS недостижима; достигается `virtual` / постраничностью.
* «Выбрать всё» стало линейным по коду (`Set` вместо `selectedRows.includes` на каждую строку), но на 1000–10 000 строк в `all` его время всё равно определяет браузер.
* Найдены и описаны проблемы вне TableGrid (§7): CSS `:nth-last-child(-n + 2)` (раскрытие строки 792 → 161 мс без него), `Pagination` → `Select` → Popper (синхронный пересчёт всей таблицы при монтировании и на каждый scroll),
  захардкоженные `grid-row-start: 1000 / 900`, повторная раскладка после загрузки веб-шрифта.

## 3. Как измеряли

* Сборка сценария S3 Vite (production, oxc, Lightning CSS) дважды: с оригинальным `src/lib/components/TableGrid` («до», копия сохранена до правок) и с текущим («после»); остальная библиотека одна и та же.
  Скрипт-обёртка запускает настоящий `tools/bench/runtime.py` с подменённой папкой сборок (сам `runtime.py` не менялся).
* Профили: CDP `Profiler` (интервал 200 мкс) и `Performance.getMetrics` на несобранной (`minify: false`) сборке, чтобы видеть имена функций; трассировка (`devtools.timeline`) для `UpdateLayoutTree` / `Layout`;
  подсчёт принудительных раскладок обёрткой над `offsetParent` / `getBoundingClientRect` / `getComputedStyle`.
* Разбор «пол браузера»: тот же DOM (`#app.innerHTML`, 1000 строк) вставляется обратно без JS, стили отключаются по листам / по правилам / по группам правил.
* Одинаковость DOM после правок: `#app` без комментариев и с отсортированными атрибутами «до» и «после» совпадает побайтно — S3 (40 строк; с ресайзом / переносом / sticky; постранично; пустая таблица) и отдельный фикстурный сценарий
  (ячейки `{ content, warning | error }`, булевы / `null` / `0` значения, `key` ≠ `name`, `render`-колонка, `stickyEnd`, `textWrap`, `alignCells`, размеры `m` / `s`, цвета строк, выбор, раскрытие, подвал), в том числе после клика по строке,
  раскрытия, сортировки, чекбокса, наведения на заголовок; плюс `python tools/compare.py` (см. §8).

## 4. Куда уходит время (1000 строк × 8 колонок, `all`)

| этап | до | после |
|---|---|---|
| JS: построение DOM (`mount()` до конца синхронной части) | ≈ 1 330 мс | ≈ 860 мс |
| пересчёт стилей (19 300 элементов) | ≈ 860 мс | ≈ 870 мс |
| раскладка (1000 auto-строк × 9 элементов в одной сетке) | ≈ 500 мс + ещё ≈ 530 мс после загрузки веб-шрифта («Fonts changed», `font-display: swap`) | то же |
| память (JS heap после GC) | 82 МБ | 55 МБ |

**«Пол» браузера.** Тот же DOM, вставленный через `innerHTML` без JS: разбор HTML 0,12 с + пересчёт стилей и раскладка 1,4–1,5 с. Из них:

* правила `tablegrid.css` (селекторы вида `.atmr-tablegrid.atmr-tablegrid--size-m .atmr-tablegrid__layout .atmr-tablegrid__cell ...`) ≈ 0,6 с пересчёта стилей (без них 0,32 с; без всех листов 0,19 с);
* инлайновое `style="--column-index: var(--column-<имя>)"` на каждой из 8000 ячеек ≈ 0,45 с (без него стили 0,47 с вместо 0,93 с; у темы 2888 custom property, вероятная причина — копирование набора унаследованных переменных для каждого элемента, который объявляет свою);
* раскладка одной сетки на 8000 элементов ≈ 0,5 с.

Всё это следствие DOM и CSS оригинала (инлайн `--row-index` / `--column-index`, `display: contents`-строки), поэтому сам по себе TableGrid на эту часть повлиять не может.
Практический вывод: **любая структурная правка сетки на 1000 строк стоит 0,5–1,9 с браузера** — сортировка (перестановка узлов + `--row-index` у каждой строки: `UpdateLayoutTree` 830 мс + `Layout` 510 мс при 160 мс JS),
«выбрать всё» (1000 чекбоксов), раскрытие (0,85 с; см. §7 про `nth-last-child`), добавление строк.

CPU-профиль JS (несобранная сборка, профилировщик включён, время включительное, 1000 строк): `TableGrid` 1 517 → 997 мс, `_LayoutColumns` 1 199 → 759, `_ContentCell` 663 → 376, `Slot` 77 → 9,
`_ExpandButton` 60 → 19, `_SelectionButton` (ui-kit `Checkbox`) 152 → 173 (не менялся); самовремя DOM-операций: `append` 212 → 111 мс, `set_style` 105 → 109, `set_attribute` 73 → 51, `set_class` 44 → 28.
Оставшиеся ≈ 0,95 мс на строку — это создание ~19 000 элементов (`append`, `set_style` на 9000 элементах) и чекбоксы.

**Что было в JS «до»** (CPU-профиль, 1000 строк; включительное время):

* `_ContentCell` — 663 мс на 8000 ячеек (83 мкс на ячейку, профилировщик включён): 7 `$derived` + 6 обращений к контексту + `clsx` + регулярки `getColumnCssKey` + компонент `Slot` + **три `addEventListener` на ячейку** (`mouseenter`, `dragover`, `drop`: 24 000 слушателей);
* `_LayoutColumns` — динамический компонент `<RenderCell>` и `{#each}` на каждую строку, `clsx` для класса addon-ячейки на каждую строку; `_LayoutRow` — `{...rest}`-spread (медленный путь атрибутов) и `clsx` + `styleToString` на каждую строку;
* `selectedRows.includes(key)` в каждом чекбоксе строки (O(n) на строку, O(n²) на «выбрать всё»), то же для `expandedRows`;
* при любом «hover» ячейки `$effect` в `_Layout` делал `querySelectorAll('.atmr-tablegrid__cell--move')` по всей таблице;
* `Pagination` → `Select` → Popper: `computePosition` читает `offsetParent` → синхронный пересчёт стилей и раскладки всей таблицы в середине `mount()` (1,5 с из 3,3 с по CPU-профилю «до» приписаны этой одной функции).
  Это не работа JS, а работа браузера, перенесённая в JS; на общее время она почти не влияет (раскладка нужна всё равно).

Все правки сохраняют DOM (проверено: см. §3 и §8).

## 6. Виртуальный режим

`virtual: { isEnable: true, overscanCount }` (типы уже были, режим не работал). Готовые списки (`VList` из `virtua/svelte`) не подходят: TableGrid — **одна CSS-сетка** (шапка, колонка чекбоксов,
sticky-шапка / подвал, ресайз / перенос колонок живут в одних и тех же треках), а `VList` кладёт каждую строку в абсолютно позиционированный блок — ячейки строки складываются в столбик, колонки не совпадают с шапкой.

Как устроено (подробно — в шапке `modules/virtual/_VirtualRows.svelte`):

```
.atmr-tablegrid__layout (grid; прокручивается)
  строка шапки                                   grid-row 2 (sticky)
  .atmr-tablegrid__virtual-window                grid-row 3, grid-template-columns: subgrid; padding-top / padding-bottom = высота пропущенных строк
    .atmr-tablegrid__virtual-row  (на каждую отрисованную строку; ResizeObserver)   subgrid; внутри обычная строка + контейнер раскрытия
  подвал
```

* окно строк и видимый диапазон считает `virtua/unstable_core` (`createVirtualStore` + `createResizer` + `createScroller`: размеры строк, смещение, компенсация «скачка» прокрутки) — то же ядро, что под `VList`;
* колонки строки — колонки сетки (subgrid), поэтому выравнивание с шапкой, ресайз, перенос, sticky-колонки работают без единой строчки специального кода; `--row-index` не пишется (auto-размещение внутри `.virtual-row`), прокрутка вставляет / удаляет **одну** строку на краю;
* высоты измеряются (раскрытая строка 179 px вместо 41 — проверено), заранее — оценка 41 px, дальше медиана измеренных;
* скроллер: `.atmr-tablegrid__layout`, если задана высота (`containerStyle` / `style`); иначе ближайший прокручиваемый родитель; иначе страница (`createWindowScroller`).

Почему каждая строка в своём `.virtual-row`, а не прямым потомком сетки: в `tablegrid.css` есть `.atmr-tablegrid__row:nth-last-child(-n + 2)` (скругление нижних углов последней строки). Пока строки — соседи, вставка / удаление строки заставляет Blink
пересчитать стили **всех** соседних строк: в первом варианте (строки — прямые потомки сетки) прокрутка стоила ≈ 21 мс стилей на кадр (350–430 элементов на кадр) = **30 fps**; при строках в отдельных `.virtual-row` — ≈ 0,7 мс на кадр = **60 fps**.
Нижние скругления последней строки восстановлены отдельным правилом (`<style>` в `_VirtualRows.svelte`); скрытый элемент после окна не даёт шапке попасть в «последние два» потомка сетки.

Проверено (сценарии Playwright вне репозитория на 3000 / 5000 / 8000 / 10 000 / 20 000 / 1 000 000 строк): выравнивание шапки и ячеек (до и после прокрутки, ресайза колонки, переноса колонки), sticky-шапка / подвал / первая колонка, выбор (в том числе «выбрать всё» на 10 000),
раскрытие с вложенной таблицей (высота измеряется), сортировка (окно остаётся на месте), смена числа строк (10 000 → 30 → 0 → 3000), бесконечная прокрутка (`loadMore` вызывается на дне, строки добавляются), скрытая шапка, PageDown / End с клавиатуры,
скролл окна страницы (20 000 строк), скролл родителя (`overflow: auto` без `containerStyle`), многократное включение / выключение `virtual` и размонтирование без ошибок; вид строк / hover / выбор / подсветка в `virtual` и `all` совпал побитно (скриншоты, 0 отличающихся пикселей).

Ограничения — в разделе «Производительность» `README.md` (нужна высота или прокручиваемый родитель, CSS subgrid: Chrome 117+ / Safari 16+ / Firefox 71+, явные ширины колонок, поиск браузера / Tab видят только отрисованные строки, предел ≈ 818 000 строк по 41 px: `scrollHeight` в Chrome ограничен 2²⁵ px, проверено на 1 000 000 строк).

## 7. Что не удалось победить в TableGrid и находки в других местах

1. **Пересчёт стилей / раскладка `all` ≈ 1,4 с на 1000 строк** — цена идентичного DOM + CSS (§4). Варианты, которые потребуют правок «вне TableGrid» и нарушат идентичность с оригиналом: переписать CSS (`content-visibility`, фиксированная высота строки),
   убрать инлайновые custom property с ячеек. Для больших списков — `virtual` / постраничность.
2. **`tablegrid.css` (сгенерирован, не правился): `:nth-last-child(-n + 2)`** — 4 правила («скругление нижних углов последней строки»). Из-за них вставка / удаление любой строки или контейнера раскрытия заставляет Blink пересчитать стили соседей:
   раскрытие строки на 1000 строк **792 мс → 161 мс, если эти правила убрать** (`UpdateLayoutTree` 609 мс по 10 016 элементам против 5 мс по 5). То же для каждой порции бесконечной прокрутки (O(строк) на каждую загрузку).
   Рекомендация владельцу: заменить на класс (`atmr-tablegrid__row--last`, он уже есть в DOM) с проверкой отсутствия футера — вид тот же, соседей не задевает. (Правка сгенерированного CSS + `tools/extract-css.py`.)
3. **`.atmr-tablegrid__footer-area { grid-row-start: 1000 }` и `.atmr-tablegrid__empty { grid-row-start: 900 }`** (из React-CSS): без `virtual` в таблице длиннее ≈ 900–1000 строк футер рисуется поверх строк (проверено: 1500 строк — футер накрывает строки около 908-й). Линии сетки после 10 000 Chromium 120 не обрезает (10 000 строк раскладываются правильно).
4. **`Pagination` → `Select` → `usePopper` (`lazy: false`)**: Popper.js живёт и в закрытом состоянии (как в React) и на каждый `scroll` предка вызывает `forceUpdate` → `offsetParent` → синхронный пересчёт. В S3 с футером это 1,5 с внутри `mount()` (1000 строк)
   и ≈ 27 % времени прокрутки `virtual`-таблицы с пагинацией (60 fps держится, запас съеден). Решение — `lazy: true` / автообновление только при открытии; это не TableGrid, не правил.
5. **Веб-шрифт** (`font-display: swap`): вторая полная раскладка (≈ 530 мс на 1000 строк) приходит по причине «Fonts changed» (трассировка `invalidationTracking`; 8000 ячеек + все чекбоксы). `<link rel="preload" as="font">` в приложении должен убрать её из первой отрисовки.
6. `src/routes/examples/crm/Organizations.svelte`: ошибка `svelte-check` (`render: (row: { status }) => ...` несовместим с `Snippet<[TableGridRow]>`) — не связана с этими правками.
